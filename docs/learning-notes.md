README.mdの「学んだ事」の詳しい説明と、ポートフォリオで説明するための全体の流れをまとめたノートです。現時点では要件定義の段階で学んだ内容を記載しています。実装と検証で学んだことは、開発後に追記します。

## 第1部 学んだことの詳しい説明

### 1. 案件文に書かれていないユーザー像を定義する

**状況**
案件文には要件と達成基準は書かれていたが、「誰が使うのか」は書かれていなかった。

**考えたこと**
市場背景の「Amazon商品リスト管理」「在庫検索」から、一般の買い物客ではなく、社内で商品データを扱う業務担当者が使うツールだと推測した。さらに、実際に在庫を確認するのは現場の人なので、スマホで使われる場面が多いと判断した。

**要件との対応**
ユーザー像を決めると、それぞれの要件が「誰のどんな困りごと」を解決するのかが見えるようになった。

| 要件 | 想定している場面 |
|---|---|
| テキスト検索＋カテゴリ絞り込み | 問い合わせを受けながら、商品名の一部だけで探す |
| 100ms以内に更新 | 入力しながら結果が絞られる。待たされると業務が止まる |
| URLで条件を共有 | 事務所が絞り込んだ一覧を、現場にチャットで送る |
| リロードしても保持 | 一日中開いていても、条件をやり直さなくていい |
| 空状態UI | 「0件なのか壊れているのか」で迷わせない |

**学び**
要件を満たすだけでなく、その要件が誰のためにあるかを考えると、UIの選択やスコープの判断に一貫した根拠を持てる。

### 2. 100ms要件と処理場所の関係

**状況**
App Routerでは、Server Componentが `searchParams` を受け取ってサーバー側で絞り込む書き方もできる。

**考えたこと**
サーバー側で絞り込むと、入力のたびにサーバーとの通信が発生し、100msを超えるおそれがある。30件程度のデータなら、ブラウザ側で `useMemo` を使って絞り込めば数msで終わる。

**判断**
データは最初に一度だけ取得し、絞り込みはクライアント側で行う。

**学び**
「どこで処理するか」は、データ量と速度要件で決まる。データが数千件以上に増えたら、サーバー側での絞り込みやページネーションへの切り替えを検討する。

---

### 3. URLを「状態の保存場所」として使う

**状況**
「リロードしても保持」「URL共有で再現」という2つの要件は、検索条件をURLに持たせれば両方満たせる。

**考えたこと**
- 入力値はReactのstateで即座に画面に反映し、URLへの書き込みは別に行う。こうすることで、URL更新を待たずに結果を表示できる。
- URLの更新には `router.push` ではなく `router.replace` を使う。`push` だと1文字入力するたびに履歴が増え、ブラウザの「戻る」ボタンが使いにくくなる。
- App Routerで `useSearchParams` を使うコンポーネントは、`<Suspense>` で囲む必要がある。

**学び**
URLは「共有できる状態」として使える。画面の状態とURLの更新を分けて考えると、速度と共有の両方を満たせる。

---

### 4. 表記ゆれ対策(NFKC正規化)

**状況**
日本語の入力では、全角/半角や大文字/小文字の違いで検索にヒットしないことがある(例:「ＵＳＢ」と「usb」)。

**判断**
検索語と商品名の両方に `normalize("NFKC")` と `toLowerCase()` をかけてから比較する。

**学び**
ひらがな/カタカナの違いはNFKCでは吸収できないため、必要なら別途対応が必要(改善点に記載)。

---

### 5. UIの方式はユーザーの使い方で決める

**状況**
カテゴリ絞り込みのUIとして、ドロップダウン、チェックボックス、タグ(チップ)の3つを比較した。

**判断**
- **タグ方式**: 選択肢が常に見えていて、選択状態がひと目でわかる。カテゴリが4〜6個なら、スマホでも1〜2行に収まる。
- **単一選択**: 現場の片手操作では、1タップで切り替わるほうが迷わない。URLも `?category=家電` の1つの値になり、処理が単純になる。

**学び**
UIの良し悪しは単独では決まらない。「誰が、どの端末で、どう使うか」と組み合わせて判断する。

---

### 6. スマホ対応を要件として明文化する

**状況**
メインユーザーを現場担当者にしたことで、スマホでの動作が必須になった。

**追加した要件**

| No | 要件 | 理由 |
|---|---|---|
| M1 | 幅375pxで横スクロールが出ない | 一般的なスマホの画面幅 |
| M2 | タップ領域は高さ44px以上 | 片手操作でも押し間違えにくい |
| M3 | 入力欄の文字サイズは16px以上 | iPhoneでは16px未満だと入力時に画面が拡大される |
| M4 | 検索エリアをsticky固定 | 一覧を下まで見た後でも、すぐ条件を変えられる |
| M5 | スマホは1列、PCは複数列 | Tailwindの `grid-cols-1 md:grid-cols-3` などで切り替える |
| M6 | Enterでキーボードを閉じる | 結果がキーボードに隠れないようにする |

**学び**
「スマホでも動く」という曖昧な目標ではなく、数値と理由を持った要件にすると、検証もしやすくなる。実機確認は `npm run dev -- -H 0.0.0.0` で起動し、同じWi-Fiのスマホから `http://PCのIPアドレス:3000` にアクセスする。

### 7. スコープの管理(在庫入力を発展版に切り出した判断)

**状況**
在庫数の入力機能を追加できないか検討した。

**考えたこと**
入力機能を加えると、アプリが「データを読む(Read)」から「データを書き換えて保存する(Update)」に変わり、保存先を決める必要が出てくる。

| 保存先 | 現場と事務所で共有できるか | 備考 |
|---|---|---|
| localStorage | ✕ | その端末でしか見えない |
| JSONファイル(Route Handler経由) | △ | Vercelなどにデプロイすると書き込めない |
| データベース(Supabaseなど) | ◯ | 実用的だが作業量が大きい |

現場と事務所でデータを共有する目的には、データベースが必要になる。しかし、この案件は1日(4時間)の初級案件で、市場背景にも「CRUDの入口」とある。

**判断**
No.06は検索・表示(Read)で完成させ、在庫入力は発展版で追加する。データ取得処理を `lib/getProducts.ts` に集約しておき、保存先の切り替えに備える。

**学び**
機能を追加できるかどうかだけでなく、「時間内に達成基準を確実に満たせるか」で判断する。後から拡張しやすい構成にしておけば、スコープを絞っても将来の追加を妨げない。

### 8. 表示項目は「現場の人が何を見て判断するか」で決める(Step 2)

**状況**
最初の案では、カードに価格と説明文も載せる予定だった。

**考えたこと**
現場の人が知りたいのは「どの商品か」と「在庫があるか」。価格や説明文は判断に使わないので、スマホの小さな画面では情報が増えるだけになる。一方で、現場では商品のバーコード番号(JANコード)で探す場面がある。

**判断**
- カードは「カテゴリ → 商品名 → JANコード」の順に表示し、在庫数を右側に大きく表示する。
- 在庫0はカード全体を赤の背景にして「在庫切れ」、1〜5個は黄の背景にして「残りわずか」のラベルを付ける。最初はラベルだけの色分けだったが、一覧をスクロールしながら探す現場では、カード全体の色のほうが目に入りやすいため変更した。さらに、パステル調では目立ちにくかったため背景を濃くした(`bg-red-300` / `bg-amber-300`)。背景を濃くするとグレーの文字が読みにくくなるので、カテゴリやJANコードの文字色も背景と同じ系統の濃い色(`text-red-900` など)に変えた。基準値 `LOW_STOCK_THRESHOLD = 5` は `lib/types.ts` に1か所だけ定義し、後から変えやすくした。
- 価格と説明文はデータからも削除した。表示していない項目で検索にヒットすると、「なぜこの商品が出たのか」がわからなくなるため、検索対象は表示している商品名とJANコードにそろえた。
- 配色は、明るい倉庫や売場で見やすいライト固定にした。

**JANコードの扱いで気をつけたこと**
- JANコードは数字だが、**文字列**として持つ。数値にすると先頭の0が消えたり、桁数が大きい値で誤差が出たりする可能性があるため。
- 13桁目はチェックデジット(読み取りミスを検出するための数字)で、前の12桁から計算して決まる。サンプルデータもこの計算に従って作成した。
- サンプルには、実在の商品と重ならないよう、店内で自由に使える先頭「20」のコードを使った。

**学び**
表示項目は「載せられるもの」ではなく「使う人が判断に使うもの」で選ぶ。検索対象と表示項目をそろえると、結果の理由がわかりやすくなる。

### 9. 読み込み中とエラーの状態も画面として設計する(Step 2)

**状況**
`fetch` でデータを取得する間や、通信に失敗したときに何を表示するかを決める必要があった。

**判断**
画面の状態を「読み込み中 / 成功 / 失敗」の3つに分け、TypeScriptの型(`LoadState`)で表した。失敗時はエラーメッセージと「再読み込み」ボタンを表示する。

**学び**
現場では電波が弱い場所もあるため、成功したときの画面だけでなく、待っている間や失敗したときの画面も設計しておくと、「画面が真っ白で何が起きているかわからない」状態を防げる。

## 第2部 ポートフォリオ説明用:全体の流れ

面接や案件の提案でこのプロジェクトを説明するときは、次の流れで話す。

### 1. 課題(何を解決したか)

> 在庫を確認するたびにExcelを開いて探すのは手間がかかり、事務所と現場で同じ情報を見るのも難しい。そこで、スマホでもPCでもすぐに商品を探せて、検索条件をURLで共有できる在庫検索アプリを作りました。

### 2. ユーザー像の設定

> 案件文にはユーザー像が書かれていなかったため、市場背景から「現場担当者(スマホ)」と「事務所の担当者(PC)」の2者を想定しました。

### 3. 主な設計判断

| 判断したこと | 選んだもの | 理由 |
|---|---|---|
| 絞り込みの処理場所 | クライアント側 | 100ms要件を満たすため |
| 検索条件の保持方法 | URLクエリ(`router.replace`) | リロード保持と共有を両立し、履歴を汚さないため |
| カテゴリUI | タグ方式・単一選択 | 現場のスマホ片手操作で迷わないため |
| カードの表示項目 | カテゴリ・商品名・JANコード・在庫数 | 現場の人が判断に使う情報だけに絞るため |
| 検索対象 | 商品名とJANコード | 表示項目とそろえ、バーコード番号でも探せるようにするため |
| スマホ対応 | 数値付きの要件として明文化 | 検証可能にするため |
| スコープ | 在庫入力は発展版へ | 4時間で達成基準を確実に満たすため |

### 4. 実装の流れ

要件定義 → プロジェクト作成とサンプルデータ → 一覧表示 → 検索と絞り込み → URL同期 → 空状態とスマホ対応 → 検証

### 5. 検証

達成基準ごとに検証方法を事前に決め、PC(DevTools)とスマホ実機の両方で確認しました。(結果は開発後に追記)

### 6. 今後の発展

> 次の段階として、Supabaseを使って在庫数を入力・保存できるようにする予定です。データ取得処理を1か所にまとめているので、保存先の切り替えだけで対応できる構成にしています。

### 説明のポイント

- 「何を作ったか」よりも「なぜそう判断したか」を中心に話す。
- 案件文に書かれていないことを自分で補って定義した点(ユーザー像、スマホ要件)をアピールする。
- スコープを絞った判断は、「できなかった」ではなく「時間と品質を守るために選んだ」と説明する。
