## 第1部 学んだことの詳しい説明

### 1. 案件文に書かれていないユーザー像を定義する

**状況**
案件文には要件と達成基準は書かれていたが、「誰が使うのか」は書かれていなかった。

**考えたこと**
市場背景の「Amazon商品リスト管理」「在庫検索」から、一般の買い物客ではなく、社内で商品データを扱う業務担当者が使うツールだと推測した。さらに、実際に在庫を確認するのは現場の人なので、スマホで使われる場面が多いと判断した。

**要件との対応**
ユーザー像を決めると、それぞれの要件が「誰のどんな困りごと」を解決するのかが見えるようになった。

| 要件 | 想定している場面 |
|---|---|
| テキスト検索＋カテゴリ絞り込み | 問い合わせを受けながら、商品名の一部だけで探す |
| 100ms以内に更新 | 入力しながら結果が絞られる。待たされると業務が止まる |
| URLで条件を共有 | 事務所が絞り込んだ一覧を、現場にチャットで送る |
| リロードしても保持 | 一日中開いていても、条件をやり直さなくていい |
| 空状態UI | 「0件なのか壊れているのか」で迷わせない |

**学び**
要件を満たすだけでなく、その要件が誰のためにあるかを考えると、UIの選択やスコープの判断に一貫した根拠を持てる。

### 2. 100ms要件と処理場所の関係

**状況**
App Routerでは、Server Componentが `searchParams` を受け取ってサーバー側で絞り込む書き方もできる。

**考えたこと**
サーバー側で絞り込むと、入力のたびにサーバーとの通信が発生し、100msを超えるおそれがある。30件程度のデータなら、ブラウザ側で `useMemo` を使って絞り込めば数msで終わる。

**判断**
データは最初に一度だけ取得し、絞り込みはクライアント側で行う。

**学び**
「どこで処理するか」は、データ量と速度要件で決まる。データが数千件以上に増えたら、サーバー側での絞り込みやページネーションへの切り替えを検討する。

### 3. URLを「状態の保存場所」として使う

**状況**
「リロードしても保持」「URL共有で再現」という2つの要件は、検索条件をURLに持たせれば両方満たせる。

**考えたこと**
- 入力値はReactのstateで即座に画面に反映し、URLへの書き込みは別に行う。こうすることで、URL更新を待たずに結果を表示できる。
- URLの更新には、履歴を増やす `push` ではなく、現在の履歴を置き換える `replace` 系を使う。`push` だと1文字入力するたびに履歴が増え、ブラウザの「戻る」ボタンが使いにくくなる。(実装では `router.replace` ではなく `window.history.replaceState` を選んだ。理由は11.に記載)
- App Routerで `useSearchParams` を使うコンポーネントは、`<Suspense>` で囲む必要がある。

**学び**
URLは「共有できる状態」として使える。画面の状態とURLの更新を分けて考えると、速度と共有の両方を満たせる。

### 4. 表記ゆれ対策(NFKC正規化)

**状況**
日本語の入力では、全角/半角や大文字/小文字の違いで検索にヒットしないことがある(例:「ＵＳＢ」と「usb」)。

**判断**
検索語と商品名の両方に `normalize("NFKC")` と `toLowerCase()` をかけてから比較する。

**学び**
ひらがな/カタカナの違いはNFKCでは吸収できないため、必要なら別途対応が必要(改善点に記載)。

### 5. UIの方式はユーザーの使い方で決める

**状況**
カテゴリ絞り込みのUIとして、ドロップダウン、チェックボックス、タグ(チップ)の3つを比較した。

**判断**
- **タグ方式**: 選択肢が常に見えていて、選択状態がひと目でわかる。カテゴリが4〜6個なら、スマホでも1〜2行に収まる。
- **単一選択**: 現場の片手操作では、1タップで切り替わるほうが迷わない。URLも `?category=家電` の1つの値になり、処理が単純になる。

**学び**
UIの良し悪しは単独では決まらない。「誰が、どの端末で、どう使うか」と組み合わせて判断する。

### 6. スマホ対応を要件として明文化する

**状況**
メインユーザーを現場担当者にしたことで、スマホでの動作が必須になった。

**追加した要件**

| No | 要件 | 理由 |
|---|---|---|
| M1 | 幅375pxで横スクロールが出ない | 一般的なスマホの画面幅 |
| M2 | タップ領域は高さ44px以上 | 片手操作でも押し間違えにくい |
| M3 | 入力欄の文字サイズは16px以上 | iPhoneでは16px未満だと入力時に画面が拡大される |
| M4 | 検索エリアをsticky固定 | 一覧を下まで見た後でも、すぐ条件を変えられる |
| M5 | スマホは1列、PCは複数列 | Tailwindの `grid-cols-1 md:grid-cols-3` などで切り替える |
| M6 | Enterでキーボードを閉じる | 結果がキーボードに隠れないようにする |

**学び**
「スマホでも動く」という曖昧な目標ではなく、数値と理由を持った要件にすると、検証もしやすくなる。実機確認は `npm run dev -- -H 0.0.0.0` で起動し、同じWi-Fiのスマホから `http://PCのIPアドレス:3000` にアクセスする。

### 7. スコープの管理(在庫入力を発展版に切り出した判断)

**状況**
在庫数の入力機能を追加できないか検討した。

**考えたこと**
入力機能を加えると、アプリが「データを読む(Read)」から「データを書き換えて保存する(Update)」に変わり、保存先を決める必要が出てくる。

| 保存先 | 現場と事務所で共有できるか | 備考 |
|---|---|---|
| localStorage | ✕ | その端末でしか見えない |
| JSONファイル(Route Handler経由) | △ | Vercelなどにデプロイすると書き込めない |
| データベース(Supabaseなど) | ◯ | 実用的だが作業量が大きい |

現場と事務所でデータを共有する目的には、データベースが必要になる。しかし、この案件は1日(4時間)の初級案件で、市場背景にも「CRUDの入口」とある。

**判断**
No.06は検索・表示(Read)で完成させ、在庫入力は発展版で追加する。データ取得処理を `lib/getProducts.ts` に集約しておき、保存先の切り替えに備える。

**学び**
機能を追加できるかどうかだけでなく、「時間内に達成基準を確実に満たせるか」で判断する。後から拡張しやすい構成にしておけば、スコープを絞っても将来の追加を妨げない。

### 8. 表示項目は「現場の人が何を見て判断するか」で決める(Step 2)

**状況**
最初の案では、カードに価格と説明文も載せる予定だった。

**考えたこと**
現場の人が知りたいのは「どの商品か」と「在庫があるか」。価格や説明文は判断に使わないので、スマホの小さな画面では情報が増えるだけになる。一方で、現場では商品のバーコード番号(JANコード)で探す場面がある。

**判断**
- カードは「カテゴリ → 商品名 → JANコード」の順に表示し、在庫数を右側に大きく表示する。
- 在庫0はカード全体を赤の背景にして「在庫切れ」、1〜5個は黄の背景にして「残りわずか」のラベルを付ける。最初はラベルだけの色分けだったが、一覧をスクロールしながら探す現場では、カード全体の色のほうが目に入りやすいため変更した。さらに、色は最初はパステルカラーだったが、原色に近い色合いに変えた(`bg-red-300` / `bg-amber-300`)。視認性を高め、現場の人が在庫の状況を判断しやすくするために配慮した。背景を濃くするとグレーの文字が読みにくくなるので、カテゴリやJANコードの文字色も背景と同じ系統の濃い色(`text-red-900` など)に変えた。基準値 `LOW_STOCK_THRESHOLD = 5` は `lib/types.ts` に1か所だけ定義し、後から変えやすくした。
- 価格と説明文はデータからも削除した。表示していない項目で検索にヒットすると、「なぜこの商品が出たのか」がわからなくなるため、検索対象は表示している商品名とJANコードにそろえた。
- 配色は、明るい倉庫や売場で見やすいライト固定にした。

**JANコードの扱いで気をつけたこと**
- JANコードは数字だが、**文字列**として持つ。数値にすると先頭の0が消えたり、桁数が大きい値で誤差が出たりする可能性があるため。
- 13桁目はチェックデジット(読み取りミスを検出するための数字)で、前の12桁から計算して決まる。サンプルデータもこの計算に従って作成した。
- サンプルには、実在の商品と重ならないよう、店内で自由に使える先頭「20」のコードを使った。

**学び**
表示項目は「載せられるもの」ではなく「使う人が判断に使うもの」で選ぶ。検索対象と表示項目をそろえると、結果の理由がわかりやすくなる。

### 9. 読み込み中とエラーの状態も画面として設計する(Step 2)

**状況**
`fetch` でデータを取得する間や、通信に失敗したときに何を表示するかを決める必要があった。

**判断**
画面の状態を「読み込み中 / 成功 / 失敗」の3つに分け、TypeScriptの型(`LoadState`)で表した。失敗時はエラーメッセージと「再読み込み」ボタンを表示する。

**学び**
現場では電波が弱い場所もあるため、成功したときの画面だけでなく、待っている間や失敗したときの画面も設計しておくと、「画面が真っ白で何が起きているかわからない」状態を防げる。

### 10. 絞り込みロジックを純粋関数に切り出す(Step 3)

**状況**
検索語とカテゴリで商品を絞り込む処理を、どこに書くかを決める必要があった。

**判断**
画面のコンポーネントの中ではなく、`lib/filterProducts.ts` に `filterProducts(products, query, category)` という関数として切り出した。この関数は、渡された値だけで結果が決まり、画面や state には触れない(純粋関数)。

- **検索**: 検索語と、商品名・JANコードの両方に `normalize("NFKC")` と `toLowerCase()` をかけてから、部分一致(`includes`)で比べる。「usb」で全角の「ＵＳＢ卓上扇風機」が、「ﾍﾟｰﾊﾟｰ」(半角カナ)で「ペーパータオル」がヒットする。
- **カテゴリ**: 完全一致で比べる。検索語との組み合わせは AND 条件(両方を満たす商品だけ)。
- **1語だけの検索**にした。商品数が30件と少なく、現場で使う前提でも十分なため。複数語(スペース区切り)の検索は、商品数が増えたときの改善点とした。
- **JANコード**は部分一致にした。末尾の数桁だけでも探せるようにするため。

**画面側の工夫**
- 絞り込み結果は `useMemo` で、商品・検索語・カテゴリのどれかが変わったときだけ計算し直す。
- 検索語とカテゴリは state に持ち、入力したらすぐ画面に反映する。URLへの保存は次のStep 4で追加した(11.に記載)。
- 「入力した瞬間」から「画面の更新が終わった瞬間」までの時間を `performance.now()` で計り、コンソールに出すようにした。Step 6で、100ms以内という達成基準の検証にそのまま使える。
- カテゴリのタグは、選択中のタグをもう一度押すと「すべて」に戻る。解除用のボタンを別に探さなくてよい。

**学び**
絞り込みの処理を画面から切り離しておくと、「この入力ならこの結果になる」という確認が画面を使わずにできる。AIに書かせたコードを確認するときも、関数単位で動作を試せるため安心できる。

### 11. 検索条件をURLに保存・復元する(Step 4)

**状況**
「リロードしても条件を保持」「URLを共有すると同じ結果が再現される」という2つの要件を、URLに検索条件を持たせて満たす。

**実装の流れ**
1. **読み込み**: `useSearchParams` で `?q=xxx&category=yyy` を読み、`useState` の初期値にする。リロードや共有されたURLを開いたときに、同じ条件が復元される。
2. **書き込み**: 検索語かカテゴリが変わったら、`window.history.replaceState` でURLを書き換える。このバージョンのNext.jsでは、`replaceState` が `useSearchParams` と連携するとドキュメントに書かれている。
3. **デバウンス**: 入力が止まってから0.3秒後にURLを書き換える。結果の表示はデバウンスせず、入力するたびにすぐ更新する。

**判断したこと**
- **入力欄の値はstateで持ち、URLは「書くだけ」にした。** `router.replace` でURLを更新し、その値から入力欄を読み戻す方式だと、日本語入力の変換中に文字が乱れるおそれがある。stateとURLを分けることで、100ms要件と日本語入力の両方を守れる。
- **`router.push` ではなく `replaceState` を使った。** 1文字入力するたびに履歴が増えると、「戻る」ボタンで前のページに戻れなくなる。連続入力のあとも、履歴の数(`history.length`)が変わらないことを確認した。
- **不正なURLにも備えた。** `?category=存在しない値` のように実在しないカテゴリが書かれていたら、「すべて」として扱い、データの読み込み後にURLからも取り除く。URLは外部から自由に書き換えられるので、「URLの値は信用しない」という前提で作る。
- **URLを書き込むのは、データの読み込みが終わってから。** 読み込み前はカテゴリが実在するか確かめられず、有効な条件のURLまで消してしまうため。
- **特殊文字は `URLSearchParams` に任せた。** `&` `=` `?` `#` を含む検索語も、`%26` `%3D` のように自動で変換(エンコード)され、リロードで正しく復元できる。URLの文字列を自分で組み立てると、この変換を忘れやすい。

**Suspenseが必要な理由(実際に試した)**
`useSearchParams` を使うコンポーネントを `<Suspense>` で囲まずにビルドすると、次のエラーでビルドが失敗した。

```
Error: Route "/": Next.js encountered URL data `useSearchParams()` in a Client Component outside of `<Suspense>`.
This blocks prerendering because the value is only available at runtime.
```

URLのクエリは、ページを開いたときにはじめてわかる値で、事前にHTMLを作る(プリレンダリング)段階では使えない。`Suspense` で囲むと、「URLが読めるまでは `fallback`(読み込み中…)を出しておく」と指定でき、ページの外枠を先に作っておけるようになる。開発中(`npm run dev`)はこのエラーが出ないので、**`npm run build` で確認する**ことが大切。

**学び**
URLは「状態の保存場所」であると同時に、外から書き換えられる「入力」でもある。保存する側(書き込み)と、読み込む側(復元と検証)を分けて考えると、不正な値にも強くなる。

### 12. 空状態UIと、スマホで固定する範囲(Step 5)

**AIに任せる部分と、自分で判断する部分**
案件の指示にある「AIに任せる:空状態UIのバリエーション」のとおり、AIが3つの案を図にして出し、その中から自分で選んだ。

| 案 | 内容 |
|---|---|
| A シンプル | メッセージと「条件をクリア」ボタンだけ |
| **B 条件を個別に解除(採用)** | 今かかっている条件を示し、1つずつ外せる |
| C 探し方のヒント付き | 「JANコードは一部でも探せます」などの案内を出す |

**Bを選んだ理由**
0件になる原因は、「文具」×「ライト」のような**条件の組み合わせ**であることが多い。原因がわかれば、片方だけ外して探し直せる。最初からやり直す手間を減らせるため、現場の人に向いていると判断した。

**固定(sticky)する範囲もB(検索欄だけ)にした**

| 案 | スマホ画面(高さ約600px)に占める割合 |
|---|---|
| A 検索欄とタグの全体 | 約30% |
| **B 検索欄だけ(採用)** | 実測で64px、667pxの画面の約10% |
| C 検索欄とタグ1行(横スクロール) | 約21%(右側のカテゴリが隠れる) |

現場では、下までスクロールした後に別の商品を探し直す場面が多く、検索欄がすぐ使えれば足りると判断した。PC・タブレット(768px以上)は場所に余裕があるので、検索欄とタグの全体を固定する。

**技術的に学んだこと**
- **`sticky` は、親要素の中でしか固定されない。** 検索欄の親が「検索欄とタグだけを囲む箱」だと、その箱が画面の外にスクロールした時点で固定が外れてしまう。そこで、スマホでは外側の箱を `display: contents`(自分自身の箱を作らず、中身を親の中に直接並べる指定。Tailwindでは `contents`)にして、検索欄の親を `<main>` にした。
- **画面の幅で固定の範囲を変えた。** Tailwindの `md:`(768px以上)で切り替えている。境界が正しいことを、幅767pxと768pxで実際に確かめた(767pxは検索欄だけ、768pxはタグも固定)。
- **空状態の各ボタンも、高さ44px以上にした。** 実測で44pxを確認した。条件を外すボタンには、`aria-label` で「検索語「ライト」を解除」のように何を外すかを明記した。×の絵は装飾なので、読み上げからは外している。
- **0件の表示には `role="status"` を付けた。** 画面が変わったことを、スクリーンリーダーに伝えるため。
- **共有されたURLが0件になる条件でも、空状態UIが出る。** `?q=zzz&category=家電` を直接開いて確認した。

**学び**
案を比べるときは、「どれが良さそうか」ではなく、「画面の何%を使うか」のように数字で比べると、判断の理由を説明しやすい。

### 13. 「100ms以内」をどう測り、どう確かめたか(Step 6)

**状況**
達成基準の「100ms以内に絞り込み結果が更新される」を、数字で確かめる必要があった。

**測り方を2通りにした**

| 測る場所 | 方法 | 何がわかるか |
|---|---|---|
| アプリの中 | 入力した瞬間に `performance.now()` を記録し、画面の更新が終わったときの差をコンソールに出す | Reactの処理(絞り込みと画面の組み立て)が終わるまでの時間 |
| ブラウザ | Event Timing(ブラウザが計る、操作から次の描画までの時間) | 実際に画面に描かれるまでを含めた時間 |

アプリの中の計測は手軽だが、画面に描かれる時間は含まない。そのため、ブラウザの計測も併用した。

**スマホを想定して、CPUを遅くして測った**
PCは速いので、通常の結果だけでは「スマホでも大丈夫」とは言えない。CPUを4倍・6倍遅くした状態でも測った。

| CPU | アプリ内の計測(最大) | ブラウザの計測(キー入力・タグのタップ、最大) |
|---|---|---|
| 通常 | 2.4ms | 16ms |
| 4倍遅い | 8.7ms | 40ms |
| 6倍遅い | 19.8ms | 56ms |

どの場合も100msに収まった。30件のデータをブラウザ内で絞り込む設計(学習ノート2.)が、数字でも裏付けられた。

**実機での結果**
自分のPCで、本番用に起動して測った結果は、`[検索]` のログで最大4.7msだった。自動テストの通常の結果(最大2.4ms)と同じ桁で、100msの基準には大きな余裕がある。iPhone 17とAndroid端末でも、入力しながら結果が遅れずに変わり、画面の拡大やキーボードの問題もなかった。

**数字の読み方で気をつけたこと**
ブラウザの計測では、最大136msや104msという値が出た。内訳を調べると、検索の操作ではなく、**ページの読み込み直後に起きたマウスホバーのイベント**だった。全体の最大値だけを見て「100msを超えた」と判断せず、操作の種類ごとに内訳を見たことで、原因を切り分けられた。

**開発用ではなく、本番ビルドで測った**
`npm run dev` は、開発用の仕組みが加わって動作が遅くなる。実際に使うときと同じ状態を測るため、`npm run build` → `npm run start` で測った。

**自動テストでわかることと、実機でしかわからないこと**

| 自動テストで確認できる | 実機で確認が必要 |
|---|---|
| 横スクロール、ボタンの高さ、文字サイズ、列数、固定の範囲、URLの復元 | iPhoneで入力欄をタップしたときに画面が拡大されないこと |
| 検索・絞り込みの結果、空状態、不正なURL | 片手での押しやすさ、キーボードが閉じること |
| CPUを遅くした場合の目安 | 実際のスマホの速さ、通信状況 |

自動テストの結果は「こうなるはず」を確かめたもので、実機の確認は「実際にこうなった」を確かめるもの。READMEの検証結果は、2つを分けて書いた。

**学び**
達成基準は、「どこで、何を、どう測るか」まで決めて初めて検証できる。測る場所によって数字の意味が違うので、何を測った数字なのかを必ず書き添える。

## 第2部 ポートフォリオ説明用:全体の流れ

面接や案件の提案でこのプロジェクトを説明するときは、次の流れで話す。

### 1. 課題(何を解決したか)

> 在庫を確認するたびにExcelを開いて探すのは手間がかかり、事務所と現場で同じ情報を見るのも難しい。そこで、スマホでもPCでもすぐに商品を探せて、検索条件をURLで共有できる在庫検索アプリを作りました。

### 2. ユーザー像の設定

> 案件文にはユーザー像が書かれていなかったため、市場背景から「現場担当者(スマホ)」と「事務所の担当者(PC)」の2者を想定しました。

### 3. 主な設計判断

| 判断したこと | 選んだもの | 理由 |
|---|---|---|
| 絞り込みの処理場所 | クライアント側 | 100ms要件を満たすため |
| 検索条件の保持方法 | URLクエリ(`replaceState`) | リロード保持と共有を両立し、履歴を汚さないため |
| カテゴリUI | タグ方式・単一選択 | 現場のスマホ片手操作で迷わないため |
| カードの表示項目 | カテゴリ・商品名・JANコード・在庫数 | 現場の人が判断に使う情報だけに絞るため |
| 在庫状況の色 | カード全体の背景を、原色に近い赤・黄にする(最初はパステル) | 視認性を高め、在庫の状況をひと目で判断できるようにするため |
| 検索対象 | 商品名とJANコード | 表示項目とそろえ、バーコード番号でも探せるようにするため |
| 絞り込みの実装 | 純粋関数(`filterProducts`)に切り出し | 画面から切り離して、動作を確認しやすくするため |
| URLの書き換え方 | `replaceState`(0.3秒のデバウンス)。入力欄の値はstateで持つ | 履歴を汚さず、日本語入力の変換中も乱れないため |
| 不正なURL | 実在しないカテゴリは「すべて」とし、URLも直す | 外から書き換えられる値は信用しない前提にするため |
| 空状態UI | 今かかっている条件を示し、1つずつ外せる(AIの3案から選択) | 0件の原因は条件の組み合わせが多く、やり直しの手間を減らすため |
| スマホでの固定範囲 | 検索欄だけ固定(PC・タブレットは全体) | タグまで固定すると画面の約30%を占めるため |
| スマホ対応 | 数値付きの要件として明文化 | 検証可能にするため |
| スコープ | 在庫入力は発展版へ | 4時間で達成基準を確実に満たすため |

### 4. 実装の流れ

要件定義 → プロジェクト作成とサンプルデータ → 一覧表示 → 検索と絞り込み → URL同期 → 空状態とスマホ対応 → 検証

### 5. 検証

達成基準ごとに、検証方法を事前に決めました。自動テスト(Playwright)で、CPUを遅くしたスマホ相当の条件も含めて確認し、結果を数字でREADMEに記録しました。100ms以内という基準は、アプリ内とブラウザの2通りで測り、CPUを6倍遅くしても、検索の操作は最大56msでした。実機(自分のPCと、iPhone 17・Android端末)でも確認し、PCの計測は最大4.7ms、スマホでも問題がありませんでした。

### 6. 今後の発展

> 次の段階として、Supabaseを使って在庫数を入力・保存できるようにする予定です。データ取得処理を1か所にまとめているので、保存先の切り替えだけで対応できる構成にしています。

### 説明のポイント

- 「何を作ったか」よりも「なぜそう判断したか」を中心に話す。
- 案件文に書かれていないことを自分で補って定義した点(ユーザー像、スマホ要件)をアピールする。
- スコープを絞った判断は、「できなかった」ではなく「時間と品質を守るために選んだ」と説明する。

## 第3部 振り返り

### 1. つまずいた点と、解決方法

| つまずいた点 | 原因 | 解決方法と、今後に活かすこと |
|---|---|---|
| 在庫状況の背景色を付けたのに、画面で色が変わらなかった | AIから渡されたファイルが、色を付ける前の古い版のままPCに置かれていた。ファイルの更新日時は新しかったので、見た目では気づけなかった | 正しい版を置き直した。さらに、**ファイルを置いたあとは、中身が正しい版と同じか1つずつ照合する**手順に変えた。画面で変化がないときは、コードの前に「ファイルが届いているか」を疑う |
| 開発中(`npm run dev`)は出ないエラーが、本番用のビルドでだけ出る | `useSearchParams` を `<Suspense>` で囲まないと、ビルドが失敗する。開発用の起動では、このエラーが出ない | 実際に囲まずにビルドして、エラーの内容を確認した。**機能を作ったら `npm run build` でも確認する**ことを習慣にした |
| 100msの計測で、最大136msという値が出た | 全体の最大値だけを見ると、基準を超えたように見えた | 操作の種類ごとに内訳を調べると、検索の操作ではなく、ページの読み込み直後のマウスホバーだった。**最大値だけで判断せず、内訳を見て原因を切り分ける** |
| 日本語入力の変換中に、入力欄の文字が乱れるおそれがあった | URLを書き換えて、その値を入力欄に読み戻す方式だと、変換中の文字が上書きされる場合がある | 入力欄の値はstateで持ち、URLへは書き込むだけにする設計にした(11.)。起きる前に、設計で避けた |

### 2. AIに任せた部分と、自分で判断した部分

案件の指示は、「AIに任せる:絞り込みロジック、空状態UIのバリエーション」「自分で判断する:UXとしての絞り込み順序(チェックボックス vs ドロップダウン vs タグ)」だった。それに沿って、役割を分けた。

| | AIに任せた | 自分で判断した |
|---|---|---|
| 要件・設計 | 要件の整理、想定ユーザーの推測、設計案の提示 | 想定ユーザーの確認(現場の担当者がスマホで使う)、在庫入力を発展版に回す判断 |
| UI | 空状態UIの3案、スマホで固定する範囲の3案、図での比較 | カテゴリ絞り込みのUI(タグ方式・単一選択)、空状態は案B、固定範囲は案B、ライト固定の配色 |
| 表示と仕様 | 絞り込みロジック(NFKC正規化、AND条件)、URL同期の実装 | カードの表示項目(価格・説明文は不要、カテゴリ→商品名の順、JANコードを追加)、在庫ラベルの基準(5個以下)、背景色をパステルから原色に近い色へ変える指示(視認性を高め、判断しやすくするため)、検索は1語のみ・JANは部分一致・タグに件数は不要 |
| 検証 | 自動テスト(Playwright)での確認、CPUを遅くした計測 | PCとスマホ実機(iPhone 17、Android)での確認 |
| 公開 | READMEと学習ノートの下書き、LICENSEの準備 | GitHubへの公開、Vercelへのデプロイ |

**自分で判断する場面が、特に重要だった理由**
AIは、案を複数出して比べるところまでは速いが、「どの案が使う人に合うか」は、使う場面を知っている人でないと決められない。たとえば、カードに価格や説明文を載せない、背景色をパステルから原色に近い色に変える(視認性を高め、判断を容易にするため)、といった判断は、現場で見る人の視点で決めた。AIの案をそのまま採用せず、変更や削除を指示した場面が、何度もあった。

**AIに頼むときに気をつけること**
- 出てきたコードや説明は、そのまま信じず、動かして確かめる(自動テストと実機)。
- 作ってもらったファイルが、本当に反映されているかも確認する(1.の最初の行)。
